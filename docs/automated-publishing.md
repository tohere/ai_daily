# Hacker News AI 自动发布架构

本文档定义 AI Daily 每天自动生成两篇 Hacker News 双语文章，并通过 GitHub Actions 部署到 Cloudflare Pages 的实现约定。

## 已确定的行为

- 每天执行一次自动发布任务，默认时间为 `08:00 Asia/Shanghai`。
- 每次任务必须生成并发布两篇文章；数量由 `DAILY_ARTICLE_COUNT=2` 控制。
- 数据来源优先使用 Hacker News 官方 API，不解析 Hacker News 网页 HTML。
- 候选故事来自热门故事列表，并过滤已删除、已失效、无外部链接和已经发布过的条目。
- 可以读取原始文章页面和部分 Hacker News 评论作为生成上下文，但不会把原文大段复制进生成文章。
- 每个 Hacker News item id 只能生成一次，生成文件会提交到 Git 仓库用于永久去重。
- 每篇文章同时包含中文和英文内容，并共用同一个稳定 slug。
- GitHub Actions 负责定时生成、提交生成文件、构建 Astro 和直接部署 Cloudflare Pages。
- 当前仓库发布分支为 `master`。

## 强制 AI 披露文案

披露文案不交给模型自由生成，而由程序固定写入并在文章正文之前渲染：

```text
中文：本文使用星期天AI中转站大模型，基于 Hacker News 内容自动生成。
英文：This article was automatically generated by the Weekly Day AI gateway model using content from Hacker News.
```

生成文章 JSON 必须包含完全一致的 `disclosure.zh` 和 `disclosure.en`。页面渲染时先输出披露文案，再输出模型生成的正文块，避免模型遗漏、改写或把披露放到文章中间。中文“星期天AI”和英文“Weekly Day AI”均链接到 `https://www.weekly-day.top/`，链接由页面组件渲染。

## 自动发布流水线

```text
GitHub Actions schedule / workflow_dispatch / push master
            │
            ├─ schedule 或手动生成模式
            │    1. 获取 Hacker News 候选故事
            │    2. 过滤已经使用的 hnId
            │    3. 抽取原文与讨论上下文
            │    4. 调用星期天AI中转站
            │    5. 校验两篇双语 JSON
            │    6. 提交到 master
            │
            └─ 所有触发模式
                 7. pnpm install --frozen-lockfile
                 8. pnpm build
                 9. Wrangler 上传 dist/
                10. Cloudflare Pages 发布
```

定时任务会在同一次工作流中完成生成和部署。这样即使工作流使用 `GITHUB_TOKEN` 推送生成文章后没有再次触发 push 工作流，当次任务仍会继续构建和部署。

## Cloudflare Pages 模式

采用 Cloudflare Pages Direct Upload，由 GitHub Actions 使用官方 Wrangler Action 上传 Astro 的 `dist/` 目录。Cloudflare Pages 控制台不再承担构建任务，避免 Cloudflare Git 集成与 GitHub Actions 重复部署。

建议 Pages 项目名使用 `ai-daily`，也可以通过 GitHub Repository Variable `CLOUDFLARE_PAGES_PROJECT_NAME` 修改。

## GitHub Actions 配置

### Secrets

| 名称 | 用途 |
| --- | --- |
| `WEEKLY_DAY_AI_API_KEY` | 星期天AI中转站密钥 |
| `CLOUDFLARE_API_TOKEN` | 上传 Cloudflare Pages |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare 账户标识 |

### Repository Variables

| 名称 | 示例 | 用途 |
| --- | --- | --- |
| `WEEKLY_DAY_AI_BASE_URL` | `https://gateway.example.com/v1` | OpenAI 兼容 API 根地址 |
| `WEEKLY_DAY_AI_MODEL` | 由中转站提供 | 生成文章所用模型 |
| `CLOUDFLARE_PAGES_PROJECT_NAME` | `ai-daily` | Pages 项目名称 |
| `HN_FETCH_LIMIT` | `50` | 每次读取的热门候选数 |
| `HN_MIN_SCORE` | `50` | 最低分数 |
| `HN_MIN_COMMENTS` | `10` | 最低评论数 |

`GITHUB_TOKEN` 由 GitHub Actions 自动提供，工作流会显式申请 `contents: write`，只用于提交生成的 JSON 文件。

## 本地环境变量

复制 `.env.example` 为 `.env` 并填写星期天AI中转站配置。`.env` 已被 `.gitignore` 忽略，不应提交任何真实密钥。Cloudflare 和 AI 密钥在 GitHub 上必须使用 Secrets，而不是写入 workflow 文件或 Repository Variables。

## 生成文章文件

生成结果写入：

```text
src/data/generated-posts/YYYY-MM-DD-hn-<item-id>.json
```

这些 JSON 文件会提交到仓库。Astro 构建阶段通过静态导入加载它们，并和当前手写文章合并。

每个文件包含：

- `schemaVersion`：当前固定为 `1`
- `source`：Hacker News item id、HN 链接、原文链接、标题、作者、分数、评论数和抓取时间
- `generation`：星期天AI标识、官网 `https://www.weekly-day.top/`、实际模型名称和生成时间
- `post`：slug、发布时间、双语标题、摘要、分类、标签、披露文案和结构化正文

机器可读规范位于 `scripts/schemas/generated-post.schema.json`。

## 内容选择和去重

默认选择策略：

1. 读取 Hacker News `topstories`。
2. 获取前 `HN_FETCH_LIMIT` 个 item。
3. 仅保留 `type=story`、存在外部 URL、未被删除且未被标记为 dead 的条目。
4. 按分数、评论数和发布时间综合排序。
5. 扫描 `src/data/generated-posts/*.json`，排除已经出现的 `source.hnId`。
6. 依次尝试候选故事，直到获得两篇通过校验的文章。

如果无法得到两篇有效文章，任务失败且不提交半成品，也不覆盖当天已经生成的文件。

## 内容与来源要求

- 生成内容应是摘要、解释和评论性的重新组织，而不是原文翻译或大段复制。
- 页面必须显示原始文章链接和 Hacker News 讨论链接。
- 模型不得虚构作者、数字、产品能力或未出现在上下文中的事实。
- 无法读取原文时可以使用 HN 元数据和讨论生成短文，但文章中要明确上下文有限。
- 原始网页内容只在工作流运行时作为生成上下文使用，不提交抓取到的全文。

## 失败与重试策略

- Hacker News 请求、原文抓取和 AI 请求使用有限次数的指数退避重试。
- 单个候选失败时继续尝试下一个候选，不直接终止整个任务。
- 模型响应必须经过 JSON 解析、字段校验、披露文案校验和 slug/hnId 去重。
- 两篇文章都准备完成后才写入正式目录，保证一次任务是原子的。
- 部署失败时保留已经提交的文章，可手动重新运行部署。
